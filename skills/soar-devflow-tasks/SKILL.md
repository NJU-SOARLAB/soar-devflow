# SOAR DevFlow — 飞书过程管理

面向大型项目的日常开发进度管理规程。当前项目的飞书链接与表格 ID 保存在目标仓库本地 `.soar-devflow/tasks.json` 与 `.soar-devflow/notifications.json`（兼容 `docs/development_management/registry.json`）。

> 如果项目还没有配置文件，先使用技能 `soar-devflow-setup` 完成初始化。

## 何时触发（动工前先挂单）

在动手修改代码前，先判断本次工作属于哪一类：

| 工作类型 | 动作 |
| --- | --- |
| 新功能、性能优化、跨模块重构、需回归或人工/实物验收的独立交付 | **必须先挂单**：查远端去重，调用 `create_task.py` 新建主/子任务与唯一任务文档（或在已有任务下续作），交付后同步并通知 |
| 一般小 bug、文案/样式/参数小修（无需独立排期与验收） | **记滚动小修**：在配置指定的 `minor_fixes_task_id`（如 `PRJ-00`）任务文档追加一行「日期 / 问题 / 提交 / 验证」，不零碎建单 |
| 纯问答、架构讨论、只读调研、规则微调 | **不建单**；仅在用户明确要求立项或拆解计划时才建单 |

**多项目工作区（多子仓）**：若同一工作区下包含多个子仓库（如 `repo-a/` 与 `repo-b/`），每个子仓维护各自的配置。执行 `create_task.py`、`sync_tasks.py`、`notify_delivery.py` 时，须在目标子仓目录下运行或显式传入 `--config <子仓>/.soar-devflow/tasks.json`（或 `docs/development_management/registry.json`），严禁把 A 项目任务写进 B 项目清单。

## 内容分工（唯一事实源）

| 内容 | 唯一维护位置 |
| --- | --- |
| 标题、负责人、日期、完成状态、领域分组、父子与原生前置 | 协同平台原生任务清单（当前内置飞书/Lark 适配器） |
| 需求、用户原话、进度、反馈、版本、测试证据、验收与局限 | 每个主/子任务唯一的任务主文档 |
| 过程状态、阶段、优先级、AI/人工双口径估算与链接 | 多维表格（Base）结构化索引；看板与甘特复用同源数据 |
| 讨论、方案推敲、关键思路 | 独立讨论笔记，任务文档引用原文，不整段抄录聊天记录 |
| 教程、系统说明、接口/协议与重要定义 | 仓库 `docs/site/` 单源 Markdown（见技能 `soar-devflow-docs`） |
| 架构设计、关键算法等精选技术资料 | 从同一仓库 Markdown 源稿整份导入在线文档，不另写第二稿 |

取消“每任务建本地过程 Markdown”和“全量双文档互查”的无效内耗。文档分工与同源发布细则见 [文档桥接](references/doc-bridge.md)。

## 日常执行规程

1. **定位与开工。** 先读取目标仓库 `.soar-devflow/tasks.json`（或兼容路径 `docs/development_management/registry.json`）定位资源坐标。已知任务 GUID 时直接读取目标任务及主文档；未知时先检索去重并核对清单归属。只核实实际必需的前置产物；保留其他会话或人工修改，绝不用本地静态快照覆盖远端最新状态。
2. **按范围记账与一键建单。** 跨模块、多步骤、架构调整、性能优化或需人工/实物验收的独立交付才新建主/子任务；子任务只按可独立交付验收拆分。新建任务优先使用配套建单脚本（先 `--dry-run` 核对编号与分组），自动完成去重检查、自动递增编号、创建并归档唯一任务文档、创建原生任务、挂载汇总页任务块并更新 `task_documents.json`：
   ```bash
   python3 <skills_dir>/soar-devflow-tasks/scripts/create_task.py \
     --title "<任务标题>" --section "<领域分组>" --due YYYY-MM-DD --dry-run
   ```
   一般小 bug、文案/参数微调只在项目配置中指定的滚动小修任务（`minor_fixes_task_id`，如 `PRJ-00`）的唯一文档追加一行「日期 / 问题 / 提交 / 验证」，不零碎建单。纯问答与规则小修不建单。
3. **集中更新。** 通常开工与交付各更新一次；中途仅在阻塞、范围变化或关键阶段结论出现时更新。任务主文档保留：目标与范围、用户原话（带日期原样引用，子任务注明摘自父需求）、必要验收标准、当前进度、真实证据与局限；不写工具调用流水账。
4. **交付、留痕与真实验收。** 每次交付在任务主文档写入固定格式的一行提交记录，并将同一行写入 Base“证据链接”，便于后续会话与 `git log --grep <编号>` 反查：
   ```text
   提交：<仓库> <分支> <起>..<止>（合入 <主干合并提交>；版本 <版本>）
   ```
   Git 提交首行以任务编号开头（如 `PRJ-12: ...`）。
   - 自动检查能完整判定且真实全部通过的任务，由 Agent 使用真实 GUID 完成原生任务（`task +complete`）。
   - 涉及设计判断、主观体验、硬件/实物或外部评审的部分保留未完成并标“待人工验收”，如实列出未运行项与局限。
   - 严禁把“代码写完 / 本地跑通 demo / 检查跳过或失败”写成验收通过；严禁仅改多维表格状态冒充原生任务完成。
5. **批次末同步与主动通知。** 发生新建、完成、改期、分组或依赖变更后，在批次末尾运行一次同步脚本：
   ```bash
   python3 <skills_dir>/soar-devflow-tasks/scripts/sync_tasks.py
   ```
   返回 `next_run_updates_links: true` 时等待新记录在 Base 可见后补跑一次，不重复创建。同步只镜像结构化事实、更新汇总页 HTML5 总览与待办/已完成分区，不代替验收、不关闭任务。每项可审阅交付由当前 Agent 主动调用 [交付通知](references/notifications.md)。

## 关键边界

- **前置只表达因果必要条件**：缺少 A 会令 B 无法实施才建立原生 `prev` 依赖；人工等待、文档排版、偏好顺序不阻塞无关任务。前置未关单但必需接口/产物已就绪时可继续。
- **计划不授权实施，关单不授权上线**：记录或拆解计划不等于授权直接修改生产/发布环境；涉及版本发布或稳定服务切换须遵循目标仓库的发布规则与人工授权。
- **优先局部读写**：已知坐标不每轮全量拉表；只回传摘要、变更项与异常，不把整份 JSON 倾倒进上下文。`ok=true` 仍须检查局部失败与警告；结果不明先查远端，绝不盲目重试导致重复建单。
