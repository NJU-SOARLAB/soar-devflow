# SOAR DevFlow — 技术文档站与教程编写

面向大项目的技术文档与教程写作规范。目标是写出**跟当前源码一致、能照着一步步跑通、配图清楚、没有断链废话**的工程文档。

项目文档配置保存在当前仓库 `.soar-devflow/docs.json`。如果项目还没有建文档站，先用技能 `soar-devflow-setup` 生成 VitePress 文档站。

## 单一事实源原则

- 教程、系统说明、接口/协议与配置定义**只在 `site_dir`（默认 `docs/site/`）维护一次**；双语页面互为完整译文，不算重复，严禁用 `@include` 引用另一语言文件充数。
- 站外只保留：目录 `README.md`、仓库社区文件（`AGENTS.md` / `CONTRIBUTING.md` / `CHANGELOG.md` 等）、过程/验证证据目录，以及为旧路径保留的 1–3 行指针。站点正文不得直接复制粘贴 README 段落。
- 过程流水（某天谁提了什么、哪轮改了范围）属于任务主文档（见技能 `soar-devflow-tasks`），**不写进技术正文**。

## 三类文档，三种读者

| 类别 | 目录 | 核心问题 | 写作方式 | 模板 |
| --- | --- | --- | --- | --- |
| **教程** | `guide/` | 我要做 X，一步步怎么操作？ | 任务导向、编号步骤、每步写清预期结果、配带编号标注截图 | [教程 7 段模板](references/tutorial-template.md) |
| **说明** | `reference/` | 它是怎么设计的？逻辑对不对？哪里容易踩坑？ | 设计边界、公式与坐标系、Mermaid/SVG 数据流、参数表、源码路径、复现验证、已知局限 | [说明 8 段模板](references/reference-template.md) |
| **规范** | `spec/` | 接口、协议、字段约定是什么？ | 写准字段、状态流转与报错语义，小标题加固定 `{#id}` 锚点，双语保持对齐 | [规范约定](references/spec-conventions.md) |

教程每节末尾链接“原理见 `reference/...`”，说明页给出“操作见 `guide/...`”，双向互链但不重复铺陈同一段内容。

## 事实纪律与可读性

1. **逐项对照源码与配置核实**：每个参数默认值、CLI 标志、行为与限制必须对照当前代码核对并给出文件路径；旧文档与实现冲突时以当前代码为准，并在说明页“核查发现”中如实记录。
2. **诚实标注状态**：未验收、近似实现、已知缺陷与未覆盖环境直接写清；绝不把“已接通”写成“已验收”，无法核实的内容标“待核实”。
3. **结论先行、自然可读**：开篇第一段说清这是什么、谁用、当前状态；用平实连贯段落，拒绝电报式短句堆砌与反复的防御性套话。
4. **宽表克制**：表格一般不超过 4–5 列，长解释与长代码路径移到表下方列表。
5. **避开 Vue 模板陷阱**：VitePress 将 Markdown 编译为 Vue 模板，正文中类似 `<stage>`、`<store>余量` 的裸尖括号占位符会导致构建失败，务必写成行内代码 `` `<stage>` `` 或 `&lt;stage&gt;`。

## 声明式截图与确定性门禁

- **自动页面截图与编号标注**：在 `shots/*.json` 中配置目标页面、裁剪区域与编号标注，运行脚本用无头浏览器自动生成到 `public/shots/<id>.png`（截图过程会拦截写请求，不会误改后端状态）。用法见 [截图清单规范](references/shot-manifest.md)。
- **提交前强制门禁**：修改文档后运行确定性检查与站点构建：
  ```bash
  python3 <skills_dir>/soar-devflow-docs/scripts/check_docs.py --check
  cd <site_dir> && npm run build
  ```
  检查内容包括：单源规则、README 防抄袭、Vue 未闭合标签、中英 `translationKey`/`sourceRevision` 与显式锚点 `{#id}` 完全一致、正文最小字数、教程/说明必有配图或 Mermaid/SVG、图片与站内链接有效性、以及可选的 `help-map.json` 校验。
